## Attempted route

Task103 prompt asked for a named micro-op family fuse. I tested the only apparent sub-51 shaves on the current MaxUnpool live graph:

1. Fuse the three scalar row slices plus two `Or` nodes into one reduction op.
2. Replace two binary `Or` nodes with one variadic `Max`.
3. Narrow or remove the final `Cast(BOOL -> F16)` feeding the free-output `MaxUnpool`.

Builder/probes live under `The_400_Tasks/Task_by_Task/task103/prototypes/microop_fuse_audit/`, generated by `task103_microop_fuse_probe.py`.

## Why this route is dead

ONNX schema source-read with the pinned local `onnx` package:

- `MaxUnpool` opset 9/11/13/18/20/21 only allows `tensor(float16)`, `tensor(float)`, `tensor(double)` data plus `tensor(int64)` indices; opset 22 adds only `bfloat16`. F16 is the narrowest valid MaxUnpool data type.
- `ReduceMax` only admits BOOL at opset 20+, but importing opset 20 would force modern `Slice` input tensors. Rewriting the two live input slices alone adds at least 18 initializer params; the reduction saves only 4 bytes of memory.
- `Max` admits integer types only at opset 12+, never BOOL. Casting the 3-row BOOL strip to U8/I8 and bumping opset also pays the modern-Slice initializer tax and cannot beat 51.

Therefore the named micro-op fuse family cannot produce a valid sub-51 task103 candidate.

## One remaining hypothesis

A fundamentally different final-output op that computes both complement and placement without `MaxUnpool` could still be imagined, but current evidence is poor: dynamic index selection costs an INT64 scalar, direct one-hot/Scatter/Pad formulations add params or charged canvas memory, and the prior hard record already priced the non-MaxUnpool output families at >=51.
