## Cost analysis

Live ONNX (cost=173,596): memory~149,331 + params~24,265.
- **Memory dominated** by 4 × full-grid (32,400-byte) tensors: Slice ch1-9 (v13), Flatten (v14), ScatterElements output (v25), Reshape output (v26).
- **Params dominated** by v0=(8100) projection vector and v2=(265×60)=15,900 lookup table.
- v2 cannot be reduced below 60 columns: max new output pixels per example = exactly 60 (tight, 2 examples hit the limit). Verified 2026-05-17.
- v0 has sparsity 0.07% (8094/8100 non-zero), nearly dense, cannot be sparsified.
- Dtype changes to initializers (FP16/INT16 for v0/v2) do NOT affect cost because initializers are counted by element count (params) not bytes, and are NOT counted in memory (intermediate tensors only).
- Under-15k sparse-tail breakthrough (2026-05-23): ORT rejects INT16 `Div`, so v24 keeps the per-group pack decoder arithmetic in INT32, casts only the decoded row/col/channel vectors to INT16 for the coordinate `Concat`s, and casts the final `[1,120,4]` index tensor to required INT64 for `ScatterND`. Decoding each 15-wide pack4 group separately also removes the 480-byte `[1,60]` raw INT64 concat. This saves 3,360 cost over v19 without changing the sparse-projection hidden-risk profile.

ScatterND restructuring (2026-05-17):
- Replacing Flatten+ScatterElements+Reshape with GatherND(135 pos)+ReduceSum+ScatterND eliminates Flatten(32,400B) and ScatterElements(32,400B) intermediates.
- Memory saved: ~64,800 bytes. But v2 must expand to (265,60,4) INT64 = 63,600 params (+47,700).
- v0 replaced by GatherND_idx(135,4)=540 + proj_w(135)=135 params, saving 7,425 params.
- Net: −63,716 memory + 40,275 params = −23,441 cost → 150,292 → +0.144 pts. BUT fails adversarial.

This route is only worth revisiting if key detection can be collapsed into a much smaller arithmetic/Conv predicate or if dynamic scatter coordinates can be generated without full INT64 rank-4 tensors.
- **Dead conv source-detector family fails the new synth gate (tested 2026-05-24)**: `task285_conv5_source_scatterlabel.onnx`, `task285_conv4x9_source_scatterlabel_sim.onnx`, and `task285_conv4x9_flatdelta2_source_scatterlabel_sim.onnx` each scored 198/500 on independent task-shaped synth seed `285405`. The failure is not just missing unseen offsets: cases using only the old visible offset set were still only 405/977 in a 1000-case breakdown. Root cause is the visible-trained local source detector, not the reflection rule.
- **Structural source detector floor (tested 2026-05-23)**: the current cropped valid-conv version verifies 265/265 at 24,512 after the 4x9 asymmetric source detector, flat-delta coordinate tail, source flat-delta sampling, and `onnxsim` polish. Dominant remaining wall is still `Cast(input -> UINT8)` = 9,000 bytes plus `source_score [1,4,27,22]` = 2,376 and the TopK bridge = 2,376. Getting below 20k likely requires eliminating the full one-hot input cast or replacing the four-channel source detector with a genuinely structural scalar/color-code detector.
- **Source-any / grouped detector compression (tested 2026-05-23)**: one-channel 5x5 source-any perceptron on one-hot features did not separate the visible+arc-gen anchors (best 213 errors). Two-channel q grouping also failed; best partition `(0,3)` vs `(1,2)` still had 43 combined errors. Retesting merged-q subsets for a three-channel collapse also failed: every pair merge leaves errors (best pairs `(0,3)` at 16 and `(1,2)` at 21). The four one-vs-q detector channels are currently necessary for this linear QConv route.
- **Scalar-label source detector (tested 2026-05-23)**: replacing the 10-channel one-hot 5x5 source detector with a 1-channel scalar-label 5x5 detector would save about 900 params, but it is not linearly separable on visible+arc-gen. Best per-q scalar-label perceptrons still had 23-37 errors, so this cannot replace the current QLinearConv source detector.
- **Wider scalar-label / cheap-feature detector (tested 2026-05-23)**: 7x7 scalar-label windows cover all visible+arc-gen source anchors but still do not separate: raw-label best errors were `[42,26,38,30]`; raw+nonzero improved only to `[26,17,22,19]`; raw+square and raw+nonzero+square were worse. The same cheap-feature tests on the 4x9 anchor also failed (`raw+nonzero` bottomed out with q2 still at 47 errors). This does not unlock the needed `input_u8` removal.
- **Single scalar color-code detector (tested 2026-05-23)**: promising in cost theory because a learned unique code per color could replace the 9,000-byte one-hot cast and reuse the code plane for painting, likely landing under 20k if exact. In practice, 40 bounded random/permutation code probes on the 4x9 window could not even separate q0; best q0 error was 42. Do not brute-force this further without a stronger optimizer for the joint code/weights problem.
- **Cheaper asymmetric one-hot source kernels (tested 2026-05-23)**: 3x9, 3x8, 8x3 and smaller valid windows were probed before the 4x9 anchor. They either have duplicate-feature conflicts or perceptron errors after hard-negative training (e.g. 3x9 `(1,4)` failed q0; 3x8 variants failed q0; 8x3 failed q0). The first exact cheaper-than-5x5 detector found was 4x9 `(1,4)`, saving only hundreds, not the 6k+ required for under 20k.
- **Scalar exact source-mask materialization (tested 2026-05-23)**: the hand rule "nonzero source cell, at least two nonzero key neighbors, different from nonzero key neighbors, outward same-color neighbor" detects source anchors exactly in numpy, but direct ONNX materialization costs 75,563 before painting because it builds full 26x26 boolean planes. Dead unless the predicate can be collapsed into a much smaller Conv/QLinearConv expression.
- **Dynamic q inference after TopK (tested 2026-05-23)**: local label-neighborhood q rule is exact on true source anchors, but replacing `GatherND(source_score, q_gather_idx)` increased cost 27,820 → 28,187 because the small label gathers and boolean tests cost more than the compact q-score gather. Do not retry unless it also enables removing source-score channels.
- **Offset pruning (tested 2026-05-23)**: all 19 outward offsets are exercised by visible+arc-gen outputs. Even rare offsets `(1,4)` and `(3,3)` each break 3 examples if removed; no safe exact offset drop remains.
- **TopK dtype bridge (tested 2026-05-23)**: ORT rejects `TopK` on `UINT8`/`INT8`; `INT32` loads but doubles the bridge memory versus the current F16 cast. Keep `score_flat -> FLOAT16 -> TopK` unless a non-TopK selector removes the cast entirely.
- **INT16 ScatterElements indices (tested 2026-05-23)**: ORT rejects `tensor(int16)` indices for `ScatterElements`. The structural label tail must keep final scatter indices as INT32.
- **Lookup scalar-label tail (tested 2026-05-23)**: converting v24's packed lookup tail to scatter scalar color labels instead of rank-4 one-hot writes scored 15,686 and only 31/265 raw-visible, because label `0` cannot distinguish active-grid background from all-zero padding outside the grid. Adding the required active-mask/padding-sentinel path costs more than the original ScatterND background-zero writes, so it does not unlock a valid sub-12k raw-one-hot lookup tail.
- **Post-task066 wallpath caution (2026-05-23)**: v16/v18/v19/v24 lookup-family candidates remain local cost diagnostics only under the radical rewrite prompt. Do not ordinary-submit any visible-pair table/pack candidate (`[265,*]` classifier rows, ConvHash+templates, sparse projection rows) as a Task285 solution; use Cherry13b identity as the public-weight disambiguator and continue looking for true structure.
- **Dtype changes to v0/v2 (FP16/INT16)**: params counted by element count (not bytes); initializers not counted in memory. Zero cost impact. Don't attempt.
- **v2 column reduction below 60**: max new pixels per example = exactly 60 (verified). Any reduction fails 265/265 gate.
- **Rank-1 approximation of v0** (channel_w × spatial_w): changes projection → adversarial failure. AND: Mul+ReduceSum intermediate is same memory as Flatten (32,400B), so no memory savings.
- **Channel-by-channel projection** (9 Slice+Mul+ReduceSum ops): doubles projection memory (each channel needs 32,400B Mul output = 9×3,600B = 32,400B + 9×Slice = another 32,400B). Strictly worse.
