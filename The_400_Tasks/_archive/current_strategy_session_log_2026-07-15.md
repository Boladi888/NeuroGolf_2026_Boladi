Round-2 confirmations: task340's 17×12 crop FAILED (grids reach 20×20, 73% wider than 12); task379's `h16×16` and `novert h20×20` both FAILED. **A crop passing visible 266/266 AND truth 2000/2000 is NOT proof of safety** — those gates can under-sample wide grids (task340's crop passed truth 2000/2000 yet failed hidden). **Before building ANY crop variant, run `corpus.build(N)['in_shapes'].max(0)`** — crop only when grids are *provably* bounded below the canvas (task070's generator-hardcoded 17×17 is the safe case; task181's tiny active region is another). Otherwise the full-size byte-equal candidate is the ship, and compression effort belongs in dtype/op-folding, not crops. keeps-highest still makes a crop a *free probe* (it can't lower the LB), but never mistake a crop's cost for the achievable floor.

> **§FILTERED-CLEAN vs LOOKUP — is a visible/held-out miss fatal? Depends on the rule class; submit-first is the judge (2026-06-01, task255/task182/task133/task265).** The held-out gate is unreliable BOTH ways:
> - **Ambiguous rule** (fill/denoise/recover; LIVE's own `ng_gate truth` < 99%) ⇒ hidden = **filtered-clean subset** (`hidden ⊆ {LIVE==gen}`). A candidate that fails *dirty* pairs can still pass hidden — **gate `ng_gate ab` / clean-only parity, NOT held-out%.** task255 v52 (17,604, worker-gate 91.8% "clean") PASSED hidden and BEAT the worker's "18,145 definitive floor" (+0.03). Gate OVER-rejected.
> - **Deterministic rule** (memorized lookup/hash, exact geometry) ⇒ hidden = **full official pair set** — **every visible pair must match; one visible miss = 0.** task182 v53 (4,683) passed `truth` 20,000/20,000 but visible 264/267 → scored **0** (the 3 "hand-crafted" pairs ARE in hidden; the generator just doesn't emit them). Gate UNDER-rejected.
> - **Corollary: `ng_gate truth` (vs the ARC-GEN generator) is NOT sufficient when the official task has pairs the generator never emits (task182/task133/task265).** Gate **byte-equal vs LIVE** (LIVE defines true hidden behavior), not just vs the generator. If dropping a fixed-visible guard is the only way under a cost target, treat it as an information probe, not a floor. And **"byte-equal to a sibling candidate" is only as correct as that sibling** (task182 v53 was byte-equal to v52 — both wrong on the 3 pairs). When unsure, submit-first costs nothing.

**Which row am I in? Test the LIVE bytes, not the csv status (task216, 2026-05-30).** Before framing a ship as an **UNLOCK** (the +13/+15 rows), confirm the *shipped* model actually FAILS on hidden — i.e. it is in the broken-on-hidden pool (000/157/209/284/388, now resolved) OR a confirmed cherry13b zero-weight family. The membership test: extract the LIVE model from `submission.zip` and run it on visible — **if it passes 266/266 visible, it is a normally-scored task** and the gain is ONLY the Path-A cost ratio (`ln(cost_old/cost_new)`, typically <1 LB), NOT a +12-ish unlock. A `NotSolved` / large-delta csv flag is **not** evidence of an unlock (the csv `solved_status` is unreliable — see §"csv solved_status field is unreliable"). task216 v8 worker spent 2 hours building a from-scratch rewrite believing it was a +12.5 unlock; LIVE passed 266/266 visible → it was a normal task and the real gain was +0.07. ## 2. Failure modes (documented in traps.md §14e)

### F1. Cross-bundle ONNX swap (proven 2026-05-24)
Swapping competitor ONNX into our submission almost always regresses. We tested:
- beicicc-6645-39 hybrid: -4598 LB
- afr1ste-6335 6-task hybrid: -86 LB

**Public-shared competitor submissions are STUBS.** The notebook publishes a placeholder; real solvers are private. The artifact's claimed LB does not match what's in the zip. **Don't cross-bundle swap. Mine notebooks for TECHNIQUES, not weights.**

### F2. "Novel op chain" rule (octaviograu 6042.85)
Rewrites that introduce new Or/And/Where/Conv chains not in the original graph can score 0 LB despite passing local verify. Rewrites that REMOVE nodes or NARROW dtypes within the existing op vocabulary score grader-exact.

**Exception** (validated 9× this session): solve-from-scratch unlocks on cherry13b=0 tasks DO introduce novel logic and DO work at 81.8% rate. The rule applies when LIVE has positive contribution.

### F6. "Different rule, different cost" scoring artifact (NEW 2026-05-25)
For Solved tasks where a candidate uses a DIFFERENT rule than current but both candidates SOLVE Kaggle hidden:

**Practical rule**: never ship a "structurally cleaner" variant that costs MORE than current. If a worker delivers a higher-cost variant, hold it as documentation only.
