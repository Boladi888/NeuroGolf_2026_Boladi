### Alpha sub-lanes (Alpha-A / Alpha-B)

Alpha was split into two sub-lanes on 2026-05-10 to enable parallel implementation work. Each sub-lane owns ~200 task IDs, balanced so the cumulative log-headroom (scoring potential) is roughly equal across lanes. The splitter supports `--lanes N` if more parallelism is needed later.

**Canonical assignment:** `The_400_Tasks/alpha_sub_lanes.md` (generated by `tools/split_alpha_lanes.py`). Re-run the splitter after a Kaggle batch lands and task costs shift:

```bash
python tools/split_alpha_lanes.py --out The_400_Tasks/alpha_sub_lanes.md
```

**First action per sub-lane (1-hour timebox).** Each Alpha sub-lane starts by picking the **worst-scoring task in its range** (highest current cost = lowest current points = most headroom) and works on it until either (a) the task's score improves by at least one organic / cost-rewrite step, or (b) one hour of attention has elapsed. If a path forward is visible after the first improvement, keep going on the same task or on the next-worst — don't stop just because a single improvement landed. If after one hour nothing has moved, document what was tried in the task's card (see "Per-task documentation" below) and pick the next-worst task.

#### Claim protocol — MANDATORY before starting any task (added 2026-05-10)

The 2026-05-10 task270 collision burned two Kaggle submissions (`grape11` regressed to 5004.63 from 5596.92, `lemon11` came back at -0.54) because both Alpha sub-lanes converged on the same recipe-ready handoff without coordination. Source: `Logs/lessons.md` 2026-05-10 "Sub-lane task270 collision". The protocol below prevents recurrence:

1. **ID-range check.** Open `The_400_Tasks/alpha_sub_lanes.md` and confirm your target task ID is in YOUR sub-lane's "Full task lists per lane" block. **The ID-range list is the single source of truth for task ownership.** No other field, recipe pointer, or `CURRENT_STATE.md` queue line overrides it. If the task is in the OTHER lane's list, do not touch it (per `01_MASTER.md` §1.20).
2. **In-flight check.** From your worktree, look at the OTHER lane's main-worktree scratch directory:
   - From an Alpha-B worktree, check `${NEUROGOLF_MAIN_ROOT}/submissions/_alpha_a_scratch/` for any file matching `taskNNN_*.py` or `taskNNN_*.onnx` for your target NNN.
   - From an Alpha-A worktree, check `${NEUROGOLF_MAIN_ROOT}/submissions/_alpha_b_scratch/` for the same.
   - **Any file there means the other lane is mid-flight on that task.** Halt and ask the owner before starting. Do NOT delete or modify the other lane's scratch contents.
3. **Recipe-ready ≠ free-pick.** Items in `CURRENT_STATE.md`'s "Recipe-ready handoffs" section are a *pool*, not a free-pick — they still belong to whichever sub-lane owns the task ID per step 1. The recipe author may pre-date the sub-lane split (e.g., May-5 recipes were filed when Alpha was a single lane); the post-split ownership applies.
4. **Cross-lane handoff.** If you genuinely need a task outside your range (e.g., your sub-lane has run out of viable work and the other lane has unclaimed candidates), file an `[A->B]` or `[B->A]` request line in `CURRENT_STATE.md`'s active queue. Do NOT pick it up unilaterally.

**Why scratch-dir as the lock signal?** Each sub-lane's `submissions/_alpha_<x>_scratch/` is shared (junctioned) into the main worktree's `submissions/` directory and is visible to both side-worktrees. A prototype file appearing there is a low-friction "I'm working on this" marker that survives across short-lived worktrees and rebases. It does not require committing or pushing to be visible to the other lane (just `ls` the path).

**Intra-Alpha file ownership** is by *task-ID range*, not by file regions:

| File | Edit policy across Alpha sub-lanes |
|---|---|
| `build_submission.py` detectors + builders | Each Alpha edits only the detectors/builders for tasks IN ITS RANGE. Shared helpers (dispatcher, cost utilities, format converters) need explicit coordination — drop a `[Alpha-X needs Alpha-Y review]` comment in a session log before touching them. |
| `build_submission.py:_collect_matches()` dispatch table | Sorted by task ID. Insert new entries in task-ID order so rebase merges trivially. |
| `tools/inspect_tasks.py:SOLVED_TASKS` literal | Same — sorted by task ID; append in numeric order. |
| `tests/test_detect.py` | Each Alpha adds tests in a `class Task<NNN>...Test` named after the specific task. Tests for tasks in different ranges don't collide. |
| `The_400_Tasks/task_state.csv` | Each Alpha edits only rows for tasks in its range. |
| `The_400_Tasks/task_cards/task<NNN>.md` | Each Alpha owns the cards for tasks in its range (creates / updates). |
| `CURRENT_STATE.md` | Sequential edits. Last submitter updates score + queue. |

**PR cadence across Alpha sub-lanes:** one PR per sub-lane per session window. If multiple Alphas have PRs ready in the same window, **serialize the merges**: first Alpha lands, second Alpha rebases onto new master before its PR opens. Stacked PRs forbidden (per `02_GIT.md` §1.4).

**Per-Alpha scratch isolation** in `submissions/`: each sub-lane writes to its own subdirectory to avoid concurrent-build races: `submissions/_alpha_a_scratch/` and `submissions/_alpha_b_scratch/`. The final `submission.zip` packaging step stays serialized (one Alpha at a time).

### Per-task documentation discipline (cross-lane)

> **Why:** As task work spreads across 3 Alphas + Beta, each task's "what's been tried, what failed, what's next" history must live somewhere a next agent can find in <500 tokens. Hunting through session logs scales badly.

Every active task (worked on by any lane in the last 7 days, OR currently in any lane's first-5 queue) has a card at `The_400_Tasks/task_cards/task<NNN>.md`. The card is the source of truth for *that task's history*; session logs are the source of truth for *that session's narrative*. They link to each other.

**Card responsibilities (per touching agent, at session end):**

1. **Create or update the card** for every task you actually touched (built, tested, debugged, mined, drafted a recipe for). One card per task.
2. **Append an Attempt row** with date / approach / result / cost / session-log link.
3. **Update the "Last touched" field** + the "Open questions" section if you left a blocker.
4. **Don't bloat.** Card stays ≤ ~40 lines; if you have more to say, put it in the session log or `Research/notes/recipe-task<NNN>.md` and link to it.
5. **Don't create cards for already-solved-and-quiet tasks** unless you're re-touching them — cards are for ACTIVE work. The `task_state.csv` row is the source of truth for "is this currently solved."

Template: `The_400_Tasks/task_cards/_template.md`. Starter cards exist for each lane's current worst task (task089 for Alpha-A, task005 for Alpha-B as of 2026-05-10). The third starter card (task175) is now Alpha-B's #2 priority.

## Worktree convention

NG uses Claude-managed worktrees (`.claude/worktrees/<name>/`), not strict per-lane paths. The "main worktree" is `${NEUROGOLF_MAIN_ROOT}` (original clone) — this is the one where post-delete `git fetch --prune` runs per `01_MASTER.md` §2.4 #6.

Branch convention: `session-YYYY-MM-DD-<lane>-<task>` (e.g. `session-2026-05-03-alpha-task050`). PR titles include `[Alpha]` or `[Beta]` prefix so review order is obvious.

---

## TODO tagging convention

Every actionable TODO across `03_PROJECT.md` and `05_BACKLOG.md` is prefixed with one of:

- `[Alpha]` — Alpha-track work (touches `build_submission.py` / `tests` / `SOLVED_TASKS`).
- `[Beta]` — Beta-track work (touches `Research/`, new `tools/*.py`, deep reads, exploit analysis).
- `[Both]` — Requires coordination; both lanes should be aware before either starts.
- `[Owner]` — Owner-only (Kaggle web actions, paste from anti-bot-blocked pages, accept rules, etc.).
- `[B→A]` or `[A→B]` — handoff: one lane did the upstream half, the other completes it. The producing lane drops the result for the receiving lane.

---

## Coordination conventions

1. **Before starting work:** read `Where I left off` in `03_PROJECT.md` and the active TODO. Pick an item from your own lane.
2. **PR shape:** each lane's work goes on its own branch off current `master` (per `02_GIT.md` §1, never directly to master). PR titles include `[Alpha]` or `[Beta]` prefix.
3. **No PR stacking** (per `02_GIT.md` §1.4, `01_MASTER.md` §1.18): PRs always have `master` as base, never each other's open branches. Sequence them — first lane lands, second rebases onto new master.
4. **The 40 currently-solved tasks must not regress.** After any Alpha-lane PR lands, run `--hybrid` and confirm all prior patterns still hit. Beta-lane PRs don't touch the build pipeline so no regression check needed there — but Beta-discoveries that rewrite the cost model should flag `[B→A]` for an Alpha follow-up.
5. **Cross-lane discoveries:** if Beta finds something Alpha needs (e.g. "task050 has a clean rule, sketch + cost estimate below"), Beta adds an `[Alpha]`-tagged TODO with the sketch + cost. Alpha picks it up. Same in reverse.
