## When to use this file

- **"Do we have data on X?"** → check the data inventory below.
- **"What is the current status of task N?"** → run `python tools/agent_helpers/show_task.py --task N` (⚠ task_state.csv is 1 MB — never Read whole).
- **"Which candidate zip should we try next?"** → use the OnnxlyFans `Team_Submission` manifest / current leaderboard state. The old `Logs/submission_candidate_digest_2026-05-08.md` and archived `The_400_Tasks/_archive/retired_top_level_ledgers_2026-06-21/submission_candidates.csv` are historical evidence only.
- **"What's the cost of pattern Y?"** → run `tools/cost_predictor.py`.
- **"Which tasks does our submission pass on arc-gen?"** → run `tools/silent_fail_check.py`.
- **"Is the dispatcher picking the cheapest match?"** → run `tools/dispatcher_audit.py`.
- **"What's the LUT key-space coverage on solved task N?"** → `tools/lut_density_check.py`.
- **"What does the unsolved-task distribution look like?"** → `python tools/inspect_tasks.py --summary` / `--unsolved [N]`.

If you're answering "what did we ship?" or "what's broken?" that's a `03_PROJECT.md` question, not this one.

## Analysis recipes

### Recipe: pre-submit checklist (codified)

**Question it answers:** is this submission safe to upload to Kaggle?
**Inputs:** current `build_submission.py` + `submissions/` + `data/competitions/neurogolf-2026/`.
**Commands (in order):**

```bash
python tools/dispatcher_audit.py                              # cheapest-match invariant
python tools/build_dispatcher_task.py 249                     # one dispatcher-picked payload; safer than build_submission.py 249
python tools/lut_density_check.py --threshold 0.05            # LUT-low tasks
python tools/arc_gen_enrich.py --tasks <ids> --num 500        # if any LOW (one-time per task)
python tools/silent_fail_check.py --min-arcgen-N 30           # silent-fail risk
python tools/_archive/task014_synthetic_guard.py <task014.onnx>        # if touching task014
python tools/_archive/task153_synthetic_guard.py <task153.onnx>        # if touching task153
python tools/cost_predictor.py --solved --verify              # calibration drift
python build_submission.py --hybrid                           # final regression
python tools/_archive/external_blend.py [--full]                       # if blending externals
cp submissions/blend.zip submissions/submission.zip           # Kaggle CLI literal-filename quirk

```

**Output:** scored Kaggle submission. Local-vs-Kaggle prediction tracks to ~0.01 precision (per `lessons.md` 2026-05-01 entry).

## Cost model — current objective + historical onnx-tool facts

Current objective is May-6 `memory+params`; the old onnx-tool facts below are retained for diagnostics and historical notes only:

- **`Where` = 0 MACs.** Free (verified at `onnx_tool/node.py:769-779`).
- **`OneHot` = 0 MACs.** Free (verified at `onnx_tool/node.py:1035-1045`).
- **`params` = element count**, NOT byte count (verified at `onnx_tool/graph.py:1393`). Sub-byte storage is futile for `params`; reused initializers count once via `params_flag_map`.
- **`memory` = the validator's custom `calculate_memory()`**, walking `value_info` byte sizes excluding `"input"`/`"output"`. NOT onnx-tool's per-node `_memory`. Single-op graphs report `memory=0`; multi-op pays ~36 KB per `[1,10,30,30]` float32 intermediate.
- **Score formula:** since the 2026-05-04 validator refresh, `points = max(1.0, 25.0 - log(max(1.0, memory+params)))` for correct networks; literal `0` for incorrect. MACs are still reported by some tools but no longer contribute to score.
- Initializers count toward `params` only, never `memory`.
- **Old constant-folding row superseded by May-6 scorer epoch.** Current official scoring no longer depends on `onnx_tool`; before using any old constant-folding or MAC-accounting note, recheck it against `_score_v2.py` / the ORT-profiler scorer.
- Full bug catalogue + 2026-04-28 host metric-update analysis: `Onnx_Advanced/scoring_internals.md#a2_cost_metric_exploits`.

**Cost-ladder cheat sheet** (from Imaad's blender; rounded):

| Op type | Approx cost | Approx pts |
|---|---|---|
| Identity (no-op) | 0 | 25 |
| Channel-Gather (color permutation) | 10 | 22.7 |
| Slice/Pad / Concat | 1.5k–36k | 17–21 |
| Spatial-Gather (length-900 int64 table) | ~3.6k + 36k | ~14 |
| 1×1 Conv | ~90k | 13.6 |
| 3×3 Conv | 810,900 | 11.4 |

## Dataset characterization

From `tools/inspect_tasks.py --summary` (snapshot 2026-05-02):

- 262 / 400 shape-preserving · 138 / 400 shape-changing.
- **3 / 400 all-30×30** — so `hflip` / `vflip` / `rot180` / binary-neighborhood-LUT restricted to those 3 are mostly inert.
- 130 / 400 introduce new colors in output (Gather alone can't add colors).
- 159 of 262 shape-preserving have output ≈ input on ≥ 80% of cells (mostly-identity-with-edits); 0 are 100% identity.
- Edit-count distribution across the 155 unsolved mostly-identity tasks: `{1-3 edits: 12, 4-10: 49, 11-30: 75, 31-100: 19, 100+: 0}`.

Sampling 5 random unsolved tasks: dominant categories are (a) extract-a-sub-pattern (large input → small 3×3 output) and (b) fill-from-seed-pixels (input has a few pixels → output has structured fill using new colors).

## Schema notes

- **Task JSON shape:** `{"train": [...], "test": [...], "arc-gen": [...]}` per `taskNNN.json`. Each pair: `{"input": grid, "output": grid}` where `grid` is a `H×W` int list with values 0–9.
- **NG ↔ ARC-AGI task mapping:** NG `taskN` corresponds to the N-th sorted-alphabetical UUID in the ARC-AGI training set (verified all 400 match on `train[0]`). Used by `tools/arc_gen_enrich.py` to pull additional procedural pairs.
- **Canvas convention:** ONNX networks operate on `[1, 10, 30, 30]` float32 tensors with the actual ARC grid embedded at the top-left and the rest zero-padded. `Identity` and `Transpose` preserve this convention; `hflip` / `vflip` via raw `Gather` do NOT for non-30×30 grids (see `lessons.md` 2026-05-01 entry).
