## Bottom-line verdict

[PRIMARY] `Cast(F32→F16)` is **safe only when you can prove that every narrowed value that can reach later arithmetic remains finite in float16, or when any overflowed value becomes an intentional `+inf` carrier that goes only into a final positivity-style comparison and cannot participate in invalid floating-point operations first**. [PRIMARY] It is **unsafe** when narrowed values can feed `Mul`, `MatMul`, `Einsum`, or similar arithmetic without an abs-max bound and a representative-input finite-output check, because ONNX `Cast` explicitly maps out-of-range floating-point values to `+/- infinity`, and IEEE-style arithmetic can then turn `inf` into `nan` through invalid operations such as `0 * inf`. [DERIVED] A visible/truth percentage can miss this failure mode because your decode is `output > 0.0`: positive infinity still decodes true, but `nan > 0.0` is not an ordered-true comparison and therefore decodes false in ONNX reference behavior and standard IEEE comparison semantics. [PROMPT] For this project, that means **`Cast-before-Gather` or `Cast-before-Slice` is not “safe by algebra” just because selected scalars match**; it is safe only after an abs-max check, a representative finite-output check, and a dataflow proof that no possible `inf` can flow into an invalid arithmetic pattern before decode. Source: ONNX Cast operator spec; Oracle Numerical Computation Guide; ONNX reference `Greater`; NumPy IEEE notes. citeturn37view1turn34view0turn15view0turn16search14

## ONNX operator semantics

[PRIMARY] ONNX `Cast` guarantees same-shape type conversion and, for non-float8 destinations, explicitly states that floating-point to floating-point conversion yields `+/- infinity` when the destination is out of range; floating-point to `bool` maps `+/- 0.0` to `False` and all other values to `True`. [PRIMARY] The same spec also warns that users must expect precision loss and value change when converting between numerical types. [DERIVED] For F32→F16 narrowing, this is the core spec-level reason you must treat overflow as a first-class semantic change, not merely a rounding change. Source: ONNX Cast operator spec. citeturn37view1turn37view2

[PRIMARY] ONNX `Gather` is an indexing operation: it indexes slices of the input tensor along one axis using integer indices and concatenates those selected slices into the output. [DERIVED] The spec describes only index-based selection, not arithmetic transformation; so `Gather` itself does not create `inf` or `nan`, but moving a `Cast` from after `Gather` to before `Gather` changes **which tensor gets narrowed**. [PROMPT] Under your cost model, that can reduce intermediate bytes, but it also means more values are exposed to F16 range limits earlier in the graph. Source: ONNX Gather operator spec. citeturn40view0

[PRIMARY] ONNX `Slice` similarly produces a slice of the input tensor along specified axes and supports all tensor element types; the spec is about slicing semantics, not arithmetic. [DERIVED] So `Cast-before-Slice` has the same basic safety logic as `Cast-before-Gather`: selector semantics are simple, but pre-selector narrowing can change range behavior earlier than before. Source: ONNX Slice operator spec. citeturn40view1

[PRIMARY] ONNX `Einsum` defines its result by a multiplication followed by a `reduce-sum` over indices not present in the output term. [PRIMARY] ONNX `Mul` is elementwise multiplication with broadcasting, and ONNX `Add` is elementwise addition with broadcasting; in each case the output has the same element type as the inputs. [DERIVED] These operator specs define the algebraic structure, but they do **not** provide a separate ONNX-specific NaN/Inf exception table, so non-finite behavior follows the floating-point semantics of the element type and the runtime’s implementation choices. Source: ONNX Einsum, Mul, and Add operator specs. citeturn39view0turn13view4turn13view5

[PRIMARY] ONNX `Where` returns elements from `X` or `Y` depending on a boolean condition. [PRIMARY] ONNX `Greater` returns a boolean tensor from an elementwise greater-than comparison, with Numpy-style broadcasting. [DERIVED] The public ONNX `Greater` page does not spell out a NaN truth table. [PRIMARY] However, the ONNX reference implementation for `Greater` delegates directly to `np.greater`, and NumPy states that it uses IEEE 754 floating-point semantics. [DERIVED] Combining those sources with IEEE unordered-comparison rules gives the practical rule that `Greater(nan, 0)` is false in ONNX reference behavior, while `Greater(+inf, 0)` is true. Source: ONNX Where and Greater operator specs; ONNX reference `op_greater.py`; NumPy IEEE notes. citeturn13view6turn40view2turn15view0turn16search14

## Floating-point facts

[SECONDARY] IEEE-754-compliant binary16 has a maximum finite magnitude of `65504`; values outside that finite range are represented using infinities rather than larger finite numbers. [PRIMARY] ONNX `Cast` aligns with this by specifying that floating-point to floating-point casts produce `+/- infinity` when the destination format is out of range. [DERIVED] Therefore the first static safety question for F32→F16 is not “does it round acceptably?” but “can any value exceed `65504` in magnitude before it reaches the next arithmetic consumer?” Source: .NET `Half` docs; ONNX Cast operator spec. citeturn33search0turn33search1turn37view1

[PRIMARY] IEEE-style floating-point treats NaN as unordered with every value, including itself. [PRIMARY] Invalid operations include `0 * infinity`, `infinity / infinity`, `0 / 0`, and unordered comparisons under the invalid-operation class. [DERIVED] In normal non-trapping execution, these invalid operations yield NaN results that then propagate through later arithmetic unless a later op explicitly overwrites or masks them. Source: Oracle Numerical Computation Guide; NumPy IEEE notes. citeturn34view0turn34view2turn16search14

[DERIVED] For your decode rule `output > 0.0`, there are three practically distinct cases. [DERIVED] A **finite positive** value decodes true in the usual way. [DERIVED] A **positive infinity carrier** also decodes true as long as it stays an ordered positive infinity until `Greater`. [DERIVED] A **NaN poison** decodes false in practice because `Greater` is not ordered-true on NaN-valued operands. [PROMPT] This is exactly why truth percentage can remain deceptively high when only a sparse subset of channels or spatial positions become NaN on real inputs. Source: Oracle Numerical Computation Guide; ONNX reference `Greater`; ONNX Greater operator spec. citeturn34view2turn15view0turn40view2

[DERIVED] Sign matters for infinities. [PRIMARY] ONNX `Cast` says overflow to floating point yields `+/- infinity` according to source sign. [DERIVED] So `-inf > 0` is false, `+inf > 0` is true, and `nan > 0` is false-in-practice under the combination of ONNX reference and IEEE unordered semantics. [DERIVED] If your graph can create both positive and negative overflow after narrowing, even “intentional infinity carriers” are not automatically safe unless sign is controlled. Source: ONNX Cast operator spec; Oracle Numerical Computation Guide; ONNX reference `Greater`. citeturn37view1turn34view2turn15view0

## ONNX Runtime CPU behavior

[PRIMARY] For ONNX Runtime v1.24.4 CPU, the `Cast` kernel converts `float -> MLFloat16` via `MlasConvertFloatToHalfBufferInParallel` and `MLFloat16 -> float` via `MlasConvertHalfToFloatBufferInParallel`. [DERIVED] So ORT’s CPU `Cast` is not a symbolic no-op: it eagerly materializes a narrowed half buffer at that point in the graph. Source: ONNX Runtime `cast_op.cc` for v1.24.4. citeturn8view0turn21view0

[PRIMARY] ONNX Runtime v1.24.4’s generated `OperatorKernels.md` shows that CPU `MatMul`, `Mul`, `Where`, and `Greater` have float16 CPU kernels, but CPU `Einsum` is listed only for `double`, `float`, `int32`, and `int64`. [PRIMARY] The ONNX spec itself allows float16 `Einsum`, so this is an ORT CPU implementation limitation rather than an ONNX language limitation. [DERIVED] For your exact target, any graph path that truly leaves an `Einsum` input in float16 on CPU 1.24.4 is not just numerically risky; it may be unsupported unless a cast back to float is inserted before `Einsum`. Source: ONNX Runtime v1.24.4 `OperatorKernels.md`; ONNX Einsum operator spec. citeturn23view0turn25view0turn25view1turn24view4turn24view2turn39view0

[PRIMARY] ORT’s CPU `Einsum` implementation performs a preprocessing pass and then a typed compute pass that explicitly wires in device helpers for `Transpose`, `MatMul`, `ReduceSum`, and `DataCopy`; pairwise operand processing is the core compute strategy. [PRIMARY] The CPU-side `Einsum` helper for `MatMul` calls `math::MatMul<T>` batch by batch. [DERIVED] That means `Einsum` is not one opaque primitive in ORT CPU; it is concretely lowered into intermediate transposes, pairwise matrix multiplies, and reductions, each of which can materialize tensors and each of which is a possible place for non-finite values to appear or propagate. Source: ONNX Runtime v1.24.4 `einsum.cc`, `einsum_typed_compute_processor.h`, and `einsum_auxiliary_ops.cc`. citeturn21view1turn27view0turn29view0turn28view0

[PRIMARY] In ORT CPU math code, `MatMul<float>` uses `MlasGemm`, while `Gemm<Eigen::half>` uses Eigen half matrix maps rather than the float MLAS GEMM path. [DERIVED] The public source visible here does **not** state a guaranteed accumulation precision for Eigen half GEMM, so for CPU float16 matmul-like work you should treat exact accumulation/promotion details as implementation-dependent unless verified against the exact ORT build and hardware. [DERIVED] That uncertainty is another reason not to approve a narrowing rewrite based only on algebraic equality of selected scalars. Source: ONNX Runtime `math_cpu.cc`. citeturn31view0

[DERIVED] The practical implication for this project is straightforward. [PROMPT] Optimization-disabled static graphs reduce optimizer-induced surprises, but they do **not** remove numeric risk from earlier `Cast` placement. [DERIVED] If you move a cast earlier, ORT will materialize a half-precision intermediate earlier; if that earlier intermediate then flows through float16-supported CPU kernels such as `Mul`, `MatMul`, `Where`, or `Greater`, you have changed the runtime’s actual numeric path, not just graph aesthetics. Source: ONNX Runtime v1.24.4 `cast_op.cc`; `OperatorKernels.md`. citeturn8view0turn21view0turn25view0turn25view1turn24view4turn24view2

## Safe narrowing conditions

[DERIVED] A narrowing rewrite is acceptable only if it passes **all three** tests below. [DERIVED] First, an **abs-max test**: every value that can reach later arithmetic after the new cast placement must satisfy `abs(x) <= 65504` on representative inputs, unless overflow is intentionally allowed and proved harmless. [DERIVED] Second, a **finite-output test**: every tensor on a path to decoded output must stay finite on representative real inputs, or any non-finite value must be a documented positive-infinity carrier that never re-enters arithmetic. [DERIVED] Third, a **no-`inf*0` downstream dataflow test**: from every node where overflow to infinity is possible, there must be no reachable invalid-op pattern such as `* 0`, `inf + (-inf)`, `inf / inf`, `0 / 0`, or any `Einsum`/`MatMul`/reduction path where zeros or sign-cancelling infinities can meet. Source: ONNX Cast operator spec; Oracle Numerical Computation Guide; ONNX Einsum and Mul specs. citeturn37view1turn34view0turn39view0turn13view4

[DERIVED] Equality checks on only the selected `Gather`/`Slice` result are insufficient for two separate reasons. [DERIVED] First, they prove only that the **selected values** are representable after narrowing; they say nothing about other values that may now be narrowed earlier because the cast moved up the graph. [DERIVED] Second, once the narrowed tensor reaches contraction-style arithmetic, ORT CPU `Einsum` uses pairwise transpose/matmul/reduce-sum helpers, so the actual intermediate tensors and the order in which non-finite values can appear are runtime-level concerns, not just symbolic-graph concerns. Source: ONNX Gather spec; ONNX Runtime v1.24.4 `einsum` sources. citeturn40view0turn27view0turn29view0

## Instrumentation recipe

[DERIVED] Use a baseline graph and the candidate narrowed graph, both on the exact target runtime family and CPU execution path. [PROMPT] Keep graph optimization disabled where possible, because you want to validate the rewritten graph you actually intend to ship, not an optimizer-altered variant. Source: project facts; ONNX Runtime versioned-kernel behavior. citeturn20view0turn21view1

[DERIVED] Use **representative real inputs**, not only synthetic one-hot sanity cases, because this failure mode is driven by real activation magnitudes and rare downstream zero/nonzero patterns. [PROMPT] Your confirmed problem already showed that visible checks and small truth gates were not enough. No external citation needed for the prompt fact.

[DERIVED] Pseudoprocedure:

- [DERIVED] For the baseline graph, expose every node output you can as a temporary graph output, or otherwise use host-side debugging hooks that let you capture each intermediate tensor.
- [DERIVED] Repeat for the candidate graph with the same input batch.
- [DERIVED] For every captured tensor, record: node name, dtype, shape, finite count, `+inf` count, `-inf` count, `nan` count, finite min/max, and finite abs-max.
- [DERIVED] Compare baseline vs candidate tensor-by-tensor where shapes align, but do **not** stop at value closeness; specifically inspect whether the candidate introduces any new non-finite values.
- [DERIVED] Compare the final raw output tensor and the final decoded boolean output (`> 0.0`) across representative real inputs.
- [DERIVED] Reject the rewrite immediately if the candidate introduces any `nan` in a tensor that can influence decoded output, or if it introduces new infinities that later pass through arithmetic without an explicit proof that they remain harmless `+inf` carriers.
- [DERIVED] If decoded outputs still match but new non-finites appear, classify the case explicitly as “harmless positive-infinity carrier” or “latent NaN risk”; never accept it as “equivalent by scalar spot-check.”

[DERIVED] The key acceptance metric is **not** merely decoded equality. [DERIVED] It is decoded equality **plus** no new NaNs on any decode-relevant path, plus either all-finite intermediates or a documented, sign-controlled, arithmetic-isolated `+inf` carrier case.
