# spatial_data_movement_catalog.md

[PROMPT] This note assumes your exact setting: hand-built ONNX graphs for roughly 30×30 grid puzzles, scored on ONNX Runtime CPU with `ORT_DISABLE_ALL`, opset `<= 20`, and a cost model of `memory = sum of trace-visible intermediate tensor bytes` plus `params = initializer element count`, with graph inputs/outputs and initializers themselves free. [PROMPT] The practical target is not “what is expressible,” but “what actually wins under your memory-plus-param metric.”

## GridSample deep-dive

[ORT-DOC][ORT-SRC] Official ONNX `GridSample` CPU support at opsets `16–20` is **source-confirmed, registry-ambiguous**. [ORT-SRC] In `core/providers/cpu/tensor/grid_sample.cc::GridSample::Compute`, ONNX Runtime registers CPU kernels for official `ai.onnx::GridSample` at `16–19` and `20–21`, with typed registrations for `float` and `double`. [ORT-DOC] The public CPU `OperatorKernels.md` table, however, clearly shows only the legacy `com.microsoft::GridSample` row in the CPU section, which is why I treat source as the definitive evidence here.

[SPEC] The grid input is normalized. [SPEC] For 2D, `grid[n, h_out, w_out, :]` is a size-2 vector of normalized positions in the source image; most values should live in `[-1, 1]`, with out-of-range positions handled by `padding_mode`. [SPEC] The output shape comes from the **shape of the grid tensor**, not from grid values: for `(N,C,H,W)` input and `(N,H_out,W_out,2)` grid, output is `(N,C,H_out,W_out)`. [PROMPT] Under your param metric, a **constant** `grid` initializer for one output plane of size `H×W` costs exactly `H·W·2` elements; at `30×30` and `N=1`, that is `1800` params before you sample a single value.

[SPEC][ORT-SRC] Border handling is exactly the usual trio: `zeros`, `border`, and `reflection`. [SPEC] `border` clamps to edge values, `zeros` returns zero outside the source, and `reflection` repeatedly reflects at the borders until coordinates return in-bounds. [ORT-SRC] The CPU source implements those semantics explicitly, including denormalization from `[-1,1]` to pixel coordinates and the reflection helper used before final clamping.

[SPEC][ORT-SRC] For exact integer-grid moves, `nearest` is the safer choice. [SPEC] Opset-20 `GridSample` says nearest rounds halfway cases to the nearest even index. [ORT-SRC] Current CPU code uses `std::nearbyint` on the denormalized coordinate for nearest sampling. [SPECULATIVE] Bilinear/linear is mathematically exact only when the sampling point lands exactly on a source pixel center so the interpolation weights collapse to `1` and `0`; in fixed-permutation puzzle work, a nearest grid is usually the more robust exactness choice.

[ORT-SRC][SPEC] A runtime-computed grid is **shape-safe** in the same important sense as a value-only Gather index tensor: if the **shape** of `grid` is fixed, then the **shape** of the output is fixed, regardless of the runtime coordinate values. [ORT-SRC] The CPU kernel literally constructs the output shape from `grid_dims[1], grid_dims[2]` in 2D and checks only that rank, batch size, and trailing coordinate dimension are consistent; it does not use coordinate values to infer shape. [ORT-SRC] Practical limitation: current CPU source supports only 4D and 5D inputs, and cubic is 4D-only.

[PROMPT][SPECULATIVE] Bottom line for your cost model: `GridSample` is a **semantic win** for true affine-ish resampling, border handling, and runtime-computed warps with fixed output shape, but it is almost always a **cost loss** for fixed flips/rotations/transposes because the constant-grid initializer alone costs `2HW` params. On a `30×30` target, that means `1800` params versus O(1) for `Slice` and O(0) for `Transpose`.

## ReverseSequence, Trilu, and EyeLike specifics

[ORT-DOC][SPEC] `ReverseSequence` is real CPU functionality, but it is usually the wrong flip primitive for full-axis puzzle flips. [SPEC] Its semantics are “reverse up to `sequence_lens[i]` along `time_axis` for each slice indexed by `batch_axis`.” [ORT-DOC] CPU support is broad at `10+`. [PROMPT][SPECULATIVE] The problem under your metric is param volume: to flip every row of an `H×W` grid horizontally, `sequence_lens` needs length `H`, so you pay `H` params, whereas a negative-step `Slice` needs only four scalar initializer elements. [PROMPT][SPECULATIVE] Therefore `ReverseSequence` beats `Slice` only in the niche case where you genuinely need **different reverse lengths per row/column** at runtime.

[ORT-DOC][SPEC] `Trilu` is one of the best “hidden golf” ops in this whole set. [SPEC] It directly zeros one triangular half relative to diagonal `k`. [ORT-DOC] CPU dtype support is narrow—`bool`, `double`, `float`, `int64`—but when your data fits, `Trilu` crushes `Range`-comparison mask builders because it is one op, zero params at `k=0`, and no intermediate planes when you apply it directly to the data you want masked. [PROMPT][SPECULATIVE] Versus a standalone `Range` construction, `Trilu` loses only when you do not have a same-shape tensor or ones-canvas to operate on.

[ORT-DOC][SPEC] `EyeLike` is similarly powerful but more conditional. [SPEC] It creates a diagonal-one matrix with the same 2D shape as the input and optional offset `k`. [ORT-DOC] CPU support at `<=20` is restricted to `double`, `float`, `int32`, `int64`, and `uint64`. [PROMPT][SPECULATIVE] Under your cost model, `EyeLike` beats `Range+Equal` whenever all three are true: you already have a same-shape 2D tensor, your dtype is in the supported set, and you want a diagonal canvas or a diagonal mask more than a packed vector. [PROMPT][SPECULATIVE] If you must fabricate the shape carrier as a full initializer, `EyeLike` can lose badly because that initializer costs `H·W` params.

[PROMPT][SPECULATIVE] The practical hierarchy is therefore simple: use `Slice` for full-axis flips; use `Trilu` for triangle masks or triangle-masked data when dtype permits; use `EyeLike` for diagonal canvases or as the first half of a diagonal-mask pattern when you already have a shape carrier. `ReverseSequence` is the niche tool, not the default.

## Blunt verdict

[PROMPT][SPECULATIVE] If I were golfing your exact cost model, I would adopt **`Slice` with negative steps**, **`Transpose`**, **`Tile`**, **`Resize` in nearest mode with `scales`**, and **`Trilu`** immediately; I would keep **`EyeLike`** as a niche bonus when its CPU dtype limits happen to fit. [PROMPT][SPECULATIVE] I would **not** reach for `GridSample` for fixed flips/rotations/transposes because `2HW` grid params are a brutal tax; I would **not** use `ReverseSequence` for ordinary flips because its `sequence_lens` vector is too expensive; and I would treat `DepthToSpace` / `SpaceToDepth`, `CenterCropPad`, `Col2Im`, and `Identity` as specialized tools that usually lose under your metric unless the representation is already channel-packed, centered crop/pad is exactly what you want, or the op is semantically forced. [PROMPT][SPECULATIVE] The short version is: **use `Slice`, `Transpose`, `Tile`, `Resize(nearest)`, and `Trilu`; admire `GridSample`, `ReverseSequence`, and `Col2Im` from a distance.**
