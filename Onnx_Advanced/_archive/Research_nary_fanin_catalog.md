# nary_fanin_catalog.md

## Scope and source classes

This note answers the prompt as an internet-only catalog of ONNX operators and ONNX Runtime CPU behavior through opset 20, with the prompt’s bans respected: no Loop, Scan, NonZero, Unique, or Compress recipes are recommended here, and index planes are counted when they exist. The counting convention used in the recipe table is the prompt’s convention: **materialized planes = trace-visible intermediate tensors only**, excluding existing inputs/initializers and excluding the final requested output; when an index/code tensor must be created, it is counted, and per the prompt its dtype must be at least INT32. [PROMPT]

Source-class tags used below are: **[SPEC]** for ONNX operator specs, **[ORT-DOC]** for ONNX Runtime’s CPU kernel registry, **[ORT-SRC]** for ONNX Runtime source code, **[SPECULATIVE]** where the implementation forces a reasonable inference but not a directly documented profiler outcome, and **[PROMPT]** for user-supplied project facts. [PROMPT]

The high-level result is that the most reliable “plane breakers” are **variadic elementwise ops**, **indexing into a pre-existing or constant bank**, **internal weighted reductions such as Conv/MatMul/Gemm**, and **single-node residue-class ops such as Mod**; by contrast, **generic k-way mux over unrelated live tensors usually does not collapse unless the candidate bank already exists**. [SPEC][ORT-DOC][PROMPT]

Two practical Q1 takeaways matter most for your cost model. First, **variadic Max/Min/Sum/Mean** and **axis reductions** are true graph-level plane breakers because they replace a pairwise tree with one output node. [SPEC][ORT-DOC]

Second, **Gather / GatherElements / GatherND** break the law only when the candidate bank already exists or is a constant initializer; if you must first materialize that bank with Concat, the saved fan-in inside the read often gets canceled by the bank materialization itself. ## Decision structures that collapse fan-in

For a **generic k-way mux over unrelated live tensors**, the surprising result is that the most obvious “fan-in breaker” often does **not** win. A `Concat`-built stack plus `GatherElements`/`GatherND` uses one read node, but it first materializes a whole bank of roughly `k × output_bytes`; under your memory model that usually costs **more** than a `Where` tree, whose intermediate cost is about `(k - 2) × output_bytes` when only intermediates are counted. So **Gather-style mux is cheapest only when the candidate bank is already present** or is a constant LUT; otherwise, generic live-tensor mux mostly preserves the law. [SPEC][ORT-DOC][PROMPT]

For a **piecewise-constant function of an integer code**, `Gather` is the cleanest win. ONNX `Gather` maps an integer tensor of indices into a table tensor, and ORT CPU supports broad data types with int32/int64 indices. If the LUT is an initializer and the code already exists, the lookup itself adds **zero intermediate planes** under your counting convention; the only cost you must count is the code/index plane if it had to be created, at **4 B/elem for INT32** or **8 B/elem for INT64**. That is usually much cheaper than any nested-Where realization of the same constant-on-code function. [SPEC][ORT-DOC][PROMPT]

For a **k-way mux from an already-stacked tensor bank**, `GatherElements` or `GatherND` is the right formulation. `GatherElements` is best when the bank is stacked on one axis and every output element needs one indexed lane from that axis; `GatherND` is best when each output element needs a full coordinate tuple or a slice read. In both cases the lookup node itself can be a zero-intermediate realization if the bank already exists, but the prompt’s ≥INT32 rule means the index plane is still a real cost whenever it is computed on the fly. [SPEC][ORT-DOC][PROMPT]

For an **arithmetic-select mux via one-hot**, there are two sharply different regimes. If the selector is **already** one-hot or already laid out as channels, then `MatMul`, `Gemm`, `Conv(1x1)`, or a 2-input `Einsum` can collapse the weighted pick into one fan-in node. If the selector is **not** already one-hot, then `OneHot(code)` materializes an expanded selector plane whose size is roughly `k × output_elems`, which usually destroys the savings unless `k` is tiny. ORT CPU also limits OneHot’s practical dtype combinations, so this is a situational optimization rather than a general mux trick. [SPEC][ORT-DOC]

For **majority / threshold of n masks**, the cheapest pattern depends on layout. If masks are already stacked as channels or columns, a **1x1 Conv**, **MatMul**, or **Gemm** does the weighted count in one node, and then a single `Greater` / `GreaterOrEqual` applies the threshold. That costs one intermediate count plane before the final boolean plane. If masks are not stacked but can be passed as distinct same-shape tensors, **variadic Sum + Greater** replaces a long add tree with exactly one intermediate count plane; on CPU, this is easiest when masks are already numeric because ORT CPU’s Sum row is not a general bool reducer. [SPEC][ORT-DOC]

For **parity / residue classes**, `Mod` is the natural primitive. ONNX `Mod` supports broadcasting and integer inputs directly, and ORT CPU documents broad numeric support through opset 20. If you already have an integer code or an integer count, `Mod(code, 2)` or `Mod(code, m)` is a zero-intermediate realization under your counting convention. If the modulus is dynamic rather than a safe constant, the prompt’s profiling rule applies: clamp the divisor with `Max(divisor, 1)` to avoid divide-by-zero faults. [SPEC][ORT-DOC][PROMPT]

For **min/max-of-many**, the answer is simple and strong: use variadic `Max` / `Min`. These are among the cleanest formal breaks of a pairwise 2-input formulation because the N-way comparison happens in one node and there is no need to build a comparison tree. In your setting, this is one of the most robust ways to beat a 2-input plane count. [SPEC][ORT-DOC]

`ScatterND` with reduction is **not** usually the cheapest dense decision primitive. Its semantics explicitly start from a copy of `data` and then apply sparse updates, so it is best when the write set is sparse and naturally expressed as updates into a base tensor. It is much less attractive than Gather/LUT/Conv/variadic-reduce formulations for dense per-cell decision logic. [SPEC][ORT-DOC]

## ORT CPU multi-operand Einsum behavior

The ONNX spec allows `Einsum` to operate on a **sequence of tensors**, so the abstract operator is truly N-ary. [SPEC]

Current ORT CPU source, however, does **not** implement a general N-ary fused contraction planner. The `EinsumTypedComputeProcessor` class explicitly documents that it “processes Einsum operands in a pair-wise fashion” and that its private `PairwiseOperandProcess` uses **Transpose, ReduceSum, and MatMul** under the hood. [ORT-SRC]

The `Run()` logic in that same source shows a special case for **one input**, and otherwise enters a loop that processes inputs “each input pair-wise”; it sets `is_final_pair = true` only on the last iteration. That means for `num_inputs >= 3`, ORT CPU forms a partial result after one pair, then feeds that partial into the next pair, rather than evaluating the full equation in one N-way fused sweep. [ORT-SRC]

Inside `PairwiseOperandProcess`, ORT CPU multiplies the prepared operands via `MatMul`, reshapes the output, and—when the pair is **not** final—may transpose the partial result into a canonical order for the next iteration. The CPU helper layer for Einsum also exposes explicit kernels for `Transpose`, `MatMul`, `ReduceSum`, `DataCopy`, and zeroing buffers. Those are strong implementation signals that multi-input Einsum is internally decomposed into auxiliary operations with partial tensors, even though they happen inside one graph node. [ORT-SRC]

That yields the following source-grounded classification. A **single-input** equation can stay inside one node and may need no partial beyond transpose/reduction helpers, depending on whether axes are merely reshaped/reordered or actually reduced; a **two-input** equation performs one pairwise contraction and may avoid a non-final transpose because the pair is final; but any **`>= 3`-operand equation** necessarily goes through the pairwise loop and therefore has at least one internal partial result between pairs. [ORT-SRC][SPECULATIVE]

For the specific form you called out, `bchw,h,w->bc`, the current source implies **not** a truly fused 3-operand contraction, but a pairwise sequence with a partial result after the first pairing and before the second. In other words, the equation is semantically elegant and may still be graph-cheap, but **source-wise it is not evidence that ORT CPU has a special N-ary fused-backend path for `>= 3` operands**. If your profiler previously showed zero trace-visible planes, the safest reading is that profiler visibility and internal allocator visibility were coarser than the source’s internal temporary structure, not that the CPU kernel avoided partials in principle. [ORT-SRC][SPECULATIVE][PROMPT]

The most defensible operational rule, therefore, is this: **treat ORT CPU `Einsum` as trustworthy for 1-input and 2-input fan-in collapsing, but do not rely on `>= 3`-operand Einsum as a guaranteed plane breaker unless you have profiler evidence from your exact ORT build and instrumentation mode.** [ORT-SRC][SPECULATIVE]

## Open questions and limitations

The biggest unresolved Q1 detail is the exact **ORT CPU dtype subset** for a few reduction-family members where the raw `OperatorKernels.md` lines were awkward to parse unambiguously from the retrieved markdown, especially **ReduceMean**, and where I could not retrieve a clean CPU row at all for **ReduceL2** and **ReduceLogSum**. I therefore marked those rows as incomplete rather than inventing a matrix. [ORT-DOC]

On **multi-operand Einsum**, the source evidence is strong that ORT CPU executes `>= 3` operands pairwise internally, but whether each internal partial appears as a “plane” in a particular profiler trace is necessarily **profile-tool dependent**. The implementation behavior is source-grounded; the profiler visibility consequence is an inference and is tagged **[SPECULATIVE]** accordingly. [ORT-SRC][SPECULATIVE]

The central practical limitation is structural, not documentary: **generic mux over separate live tensors does not really beat the law unless you can re-express the problem as lookup-from-a-bank, weighted reduction over a channel stack, or a residue/LUT function of a compact integer code.** That is the main boundary between “real breaker” and “same cost in another costume.” [SPEC][ORT-DOC][PROMPT]
