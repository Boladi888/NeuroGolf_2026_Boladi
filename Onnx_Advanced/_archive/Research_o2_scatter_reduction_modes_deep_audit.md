## Scope and executive verdict

This note audits **reduction-mode value**, not general scatter usage, under the card’s cost model `[PROMPT]`: cost is `intermediate_memory_bytes + param_elements`, graph inputs/final outputs are free, params are dtype-blind, the target runtime is **ONNX Runtime 1.24.4 CPUExecutionProvider**, and the common dense frame is `[1,C,H,W]` with `C<=10`, `H,W<=30`. On that target, the practical split is sharp: **`ScatterElements` reductions are real candidates; `ScatterND` reductions are mostly a trap.** ONNX itself allows reduced duplicate writes for `ScatterElements` from opset 16 and broadens them with `min/max` at opset 18, and does the same for `ScatterND`; but ORT CPU 1.24.4 implements `ScatterElements` as a deterministic flattened loop while `ScatterND` pushes writes through a thread-pool path that mutates the shared output buffer in parallel. That makes duplicate-target uses such as histograms, overlap stamps, and priority routing viable for `ScatterElements`, but unsafe or dead for `ScatterND` on this runtime. citeturn17view0turn17view1turn16view3turn16view4turn10view3turn10view4turn11view0turn21view0

The blunt bottom line is therefore `[DERIVED]`: **the best remaining reduction probe is not `ScatterND`; it is `ScatterElements`, especially `min`/`max` for compact first/last-position or priority-routing reducers, and `mul` on `bool` for an AND/all-present aggregator.** For `ScatterND`, the reduction shelf on ORT CPU 1.24.4 is effectively complete unless a local probe overturns the duplicate-write story. citeturn17view0turn18view0turn12view0turn13view0turn10view4

## Spec matrix

On the **ONNX side** `[PRIMARY]`, `ScatterElements` exists at opset 11 with overwrite-only semantics; opset 16 adds the `reduction` attribute with `none`, `add`, and `mul`; opset 18 expands that to `none`, `add`, `mul`, `max`, and `min`. Across these versions, the output shape is always the same as `data`, `indices` and `updates` have the same rank, `updates` matches `indices` shape, and index type is `int32` or `int64`. With `reduction="none"`, duplicate indices are forbidden by the spec; with reductions, the spec defines a fold with `f ∈ {+,*,max,min}`. Opset 11 lacks `bfloat16` in the type constraint, while 13/16/18 include it. citeturn17view2turn17view1turn17view0turn19view1turn19view2

On the **ONNX side for `ScatterND`** `[PRIMARY]`, opset 11/13 are overwrite-only; opset 16 adds `none`, `add`, and `mul`; opset 18 adds `max` and `min`. `ScatterND` always returns the same shape as `data`, always uses **`int64` indices only**, and requires `updates.shape = indices.shape[:-1] + data.shape[k:]` where `k = indices.shape[-1]`. That means it naturally writes either scalar points (`k = rank(data)`) or full trailing slices; on `[1,C,H,W]`, for example, `k=2` writes whole `[H,W]` channel planes, `k=3` writes whole `[W]` rows, and `k=4` writes scalar points. As with `ScatterElements`, overwrite mode forbids duplicates, while reduced modes are defined as folds over duplicate targets. Opset 11 again lacks `bfloat16`, while 13/16/18 include it. citeturn18view1turn16view5turn19view3turn16view3turn16view4

Two extra ORT facts matter for pricing. First, the `ScatterElements` CPU registrations are all marked `MayInplace(0,0)`, which is the explicit ORT in-place alias hint for input `data` to output; the `ScatterND` registrations shown in 1.24.4 do **not** carry that registration hint, even though the implementation avoids copying when input and output happen to share the same buffer. Second, `ScatterND`’s implementation computes `element_to_copy = input_shape.SizeFromDimension(k)` and then writes those full trailing slices, which is why it is better described as a **trailing-slice writer** than as an arbitrary patch writer. citeturn20view3turn21view0turn21view1turn12view2turn20view0turn20view1

## Cost idioms

Using the card’s cost model `[PROMPT]`, the key pricing variables are `[DERIVED]`: `N` sparse writes/events, compact output size `K`, runtime element bytes `B(T)`, and for `ScatterND` the number of addressed index dimensions `k = indices.shape[-1]`. `ScatterElements` point-bucketing usually pays **`N` index elements** (plus `N` constant updates if the updates are literals), while `ScatterND` point writes into a rank-4 `[1,C,H,W]` tensor pay **`4N` index elements** because scalar point writes require `k=4`. If `ScatterND` drops to `k=3` or `k=2`, it saves index elements but stops being a point writer and becomes a whole-row or whole-plane writer instead. That is the core pricing reason `ScatterND` looks worse than `ScatterElements` for sparse duplicate-target reducers. citeturn16view3turn20view0turn20view1turn19view3

A practical scaling anchor under `[PROMPT]` is that a full `[1,10,30,30]` intermediate contains `9000` elements, so a full **float32** scatter intermediate is about **36,000 bytes** `[DERIVED]`. Compact outputs such as `[K]`, `[K,C]`, `[K,H]`, or `[K,W]` are therefore where scatter reducers earn their keep; a full-size scatter **intermediate** usually only wins if it replaces something even denser than itself. That is exactly why one-hot stacks are vulnerable to compact `ScatterElements` reducers, while dense in-frame overlays are only selectively vulnerable.

## Collision semantics

For **`ScatterElements` on ORT CPU 1.24.4** `[PRIMARY][DERIVED]`, duplicate-target reduction behavior is usable. The ONNX spec still says overwrite mode (`reduction="none"`) should not contain duplicate indices, so overwrite overlays must keep targets unique. But for `add`, `mul`, `min`, and `max`, the ORT CPU kernel walks the flattened update space in a fixed loop and applies the reduction inline, which gives a deterministic fold order on this specific runtime. That is good enough for exact integer histograms, per-category min/max position reducers, multi-write scalar stamps along one scattered axis, and priority routing reducers. citeturn17view0turn17view1turn10view3turn11view1turn12view0

For **`ScatterND` on ORT CPU 1.24.4** `[PRIMARY][DERIVED]`, the story flips. The ONNX schema allows reduced duplicate writes starting at opset 16 and broadens them again at opset 18, but ORT’s CPU implementation first precomputes output offsets and then sends the writes through `ThreadPool::TryParallelFor`, with each worker mutating the shared output buffer directly. In the visible source there are no atomics, locks, or per-index conflict-resolution structures. That makes duplicate-target reductions unsuitable for deterministic histogramming, min/max position aggregation, overlap stamps, or priority routing. Non-overlapping writes are still fine; duplicate-target reductions are the dead zone. citeturn18view0turn16view3turn10view4turn20view0turn13view0

“Exact enough” under the card’s caveats therefore becomes simple `[PROMPT][DERIVED]`: if the result is a **count** or a **position**, prefer integer accumulators or integer payloads; if the reducer is `mul(bool)`, it is logically exact; if the result is a floating accumulation, only use it when the chosen dtype is acceptable for the exactness you need. On the target shape cap `[1,10,30,30]`, exact integer histograms are easy to keep in `int32`/`int64`, and integer position reducers are naturally exact. The real killer is not usually arithmetic exactness; it is duplicate-write determinism, especially for `ScatterND`.  

## Probe plan

A repo-access worker should close this card with a **small, surgical** probe set.

Run a **`ScatterElements(add)` histogram probe** on CPU with duplicates by bin, using `int32`, `int64`, and `float32` accumulators, and confirm deterministic repeatability across repeated session runs. The model should be tiny: output `[K]`, `K<=10`, with `N` in `{16,64,256,900}` and intentionally duplicated bins. Success criterion: exact match to a reference histogram for integer dtypes and stable repeats for float32. This validates the cleanest compact-accumulator win. citeturn17view1turn11view1turn10view3

Run a **`ScatterElements(min/max)` position probe** where a row of categories routes integer column indices into `[K]` using sentinel bases for first/last occurrence. Test both `int32` payloads and `float16` payloads, because ORT’s source blocks `bfloat16` for `min/max` here but does not block `float16`. Success criterion: exact integer answers for the integer payload case and stable results on repeated runs. This is the best likely score win if not already on the shelf. citeturn17view0turn12view0turn14view0turn14view1

Run a **`ScatterElements(mul,bool)` all-present probe** with a `true` base and duplicated writes to the same slot. The worker should verify that ORT’s CPU kernel really behaves as boolean `&=` and that the compact reducer beats the incumbent dense stack in the card’s byte+param metric for small `K`. Success criterion: exact logical agreement with a reference dense boolean reduction. citeturn11view1turn10view3

Run a **`ScatterND` duplicate-collision failure probe** for `add`, `min`, and `max`, intentionally sending many duplicate updates to the same scalar output and to the same row-slice output. Use enough work items to encourage thread-pool parallelism. Success criterion for the audit is actually **failure**: if repeated runs disagree or diverge from a single-threaded reference, the `ScatterND` reduction shelf is closed with evidence on the target runtime. citeturn10view4turn13view0turn20view0

Run a **`ScatterND` shape-limit probe** on `[1,C,H,W]` with `k=2`, `k=3`, and `k=4` to document what the op can really assemble without reshaping. Success criterion: `k=2` writes whole `[H,W]` planes, `k=3` writes whole `[W]` rows, and only `k=4` writes scalars. This prevents over-crediting `ScatterND` as an arbitrary 2-D patch writer. citeturn16view3turn20view0turn20view1

Run a **cost crossover notebook** `[PROMPT][DERIVED]` that scores `Where` overlays versus sparse scatter overlays on `[1,10,30,30]` for `N in {4,16,64,256}` and for compact outputs `[K]`, `[K,C]`, `[K,H]`, `[K,W]`. Success criterion: a table that makes it visually obvious when sparse scatter wins only because the output is compact/final, and when it loses because the full-frame scatter intermediate is charged.

## Open questions and limitations

This audit is high-confidence on **schema**, **registration**, and the visible **CPU source path**, but it is still a source audit rather than a live execution trace. In particular, the `ScatterND` duplicate-write verdict is based on the visible `TryParallelFor` implementation with direct shared-buffer mutation, not on a measured nondeterminism log from the target repo. That is why the closure probe above still matters. citeturn10view4turn13view0

I also did not audit non-CPU execution providers, ORT graph-rewrite behavior beyond the published kernel registrations, or any repo-local helper patterns that might already hide these idioms behind larger macros. The conclusions here are therefore scoped to **ONNX Runtime 1.24.4 CPUExecutionProvider** and to what can be inferred from official ONNX docs plus ORT kernel docs/source. citeturn22view1turn4view1turn21view0

## Final verdict

The best reading of the specs plus ORT 1.24.4 CPU source is `[DERIVED]`: **`ScatterElements` is the only reduction family here with real unexploited golf headroom.** `add` remains the compact accumulator for histograms and sparse bucket sums; `min/max` are strong for per-category first/last position and priority routing; and `mul(bool)` is the best underexplored niche reducer. `ScatterND` does not look like a hidden win on this runtime: it is int64-index-only, naturally limited to trailing-slice writes, and its duplicate-target reductions are poisoned by the visible parallel write path. If you want one last high-value probe, make it **`ScatterElements(reduction='mul', dtype=bool)`**; if you want one last `ScatterND` action item, make it a **failure probe** whose job is to prove the duplicate-target race and close that shelf out. citeturn19view3turn21view0turn20view0turn10view4turn17view0turn11view1
