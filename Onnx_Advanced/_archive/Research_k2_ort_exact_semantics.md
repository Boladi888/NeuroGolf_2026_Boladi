## Executive summary

[PROMPT] This note assumes onnxruntime **1.24.4**, **CPU EP only**, **graph optimizations disabled** (`ORT_DISABLE_ALL`), **onnx 1.21.0**, and **default-domain opsets 10–18**; the goal is **bit-exact post-binarization** behavior rather than approximate numerical similarity. [PRIMARY] The public GitHub tag **v1.24.4** was browsable and I used that tag for ORT CPU-kernel citations. citeturn45view0turn45view2turn45view5turn45view10

[PRIMARY] **VERIFY claim 1 — ArgMax ties/select_last_index:** **Confirmed.** ONNX ArgMax says default behavior is first-occurrence, and `select_last_index=1` selects the last occurrence. ORT’s `ReduceKernelBase` reads `select_last_index` with default `0`, and `ArgMax::Compute` / `ArgMin::Compute` branch on `select_last_index_` to dispatch different reduction specializations. Example: `ArgMax([2,5,5,1]) -> 1` by default, `-> 2` with `select_last_index=1`. citeturn43search1turn41view0turn38view2turn38view3

[PRIMARY] **VERIFY claim 2 — TopK sorted ties / sorted=0 determinism:** **Partly confirmed.** ORT’s comparator explicitly gives higher priority to the **lower original index** when values are equal, and `sorted=1` causes ORT to `std::sort` the selected top-k prefix with that comparator. Example: `TopK([9,9,7], k=2, largest=1, sorted=1) -> indices [0,1]`. [DERIVED] For `sorted=0`, ORT uses `std::nth_element` and skips the final sort, so the **membership** of the returned top-k set is determined, but the **order inside that set is an implementation detail**, not a portable semantic guarantee. citeturn50view2turn46view2turn46view1

[DERIVED] **VERIFY claim 3 — Pad negative pads as crop:** **Likely true in the common CPU kernel path; not fully source-proved for every legacy path.** ORT’s CPU `Pad::Compute` carries both `pads` and `slices` and passes both into `PadImpl(..., mode_, ...)`, which is strong evidence that cropping via negative pads is supported in the common implementation and is plumbed independently of the selected pad mode. [PRIMARY] ONNX Pad also documents that pads can be negative. [SPECULATIVE] I did not isolate the older static-attribute-only opset-10 path in the remaining extract budget, so my confidence is highest for the common opset-11+ path. Example: a 1-D pad with `pads=[-1,-1]` acts like cropping one element from each end before/while padding. citeturn50view1turn47view2turn47view3turn7view2

[PRIMARY] **VERIFY claim 4 — `Where(cond, X, Y)` with `X,Y=BOOL`:** **Confirmed for the visible v1.24.4 CPU registrations.** ORT’s CPU `where_op.cc` registers `Where` for opset 9–15 on `uint8_t`, `int32_t`, `int64_t`, `float`, `double`, and `std::string`; for opset 16 the visible registrations include `uint8_t`, `int32_t`, `int64_t`, and `float`, while `MLFloat16` and `BFloat16` are visibly commented out in the shown excerpt, and **`bool` is absent**. [DERIVED] That means `Where(cond, X, Y)` with `X,Y` of type `BOOL` should fail CPU-kernel lookup in ORT 1.24.4. Example: `Where([true,false], [true,true], [false,false])` is spec-legal ONNX, but ORT CPU registration does not show a `bool` kernel. citeturn50view0turn7view3

[DERIVED] The three highest-risk silent breakages for a bit-exact contract are: **TopK with `sorted=0`**, because ORT does not finalize an order after `nth_element`; **Where with `bool` data inputs**, because the CPU kernel is not registered even though ONNX permits the type; and **integer-domain arithmetic edge cases** such as `Pow` with integer bases/exponents and signed overflow, because ORT frequently uses native C++/Eigen operators whose edge behavior is not “model-portable semantics.” citeturn46view2turn50view0turn21view0turn22view0

### Resize formulas that matter in practice

[PRIMARY] The ONNX formulas that most often decide bit-exactness are the coordinate transform and the nearest-index rule. For a single spatial dimension, with output coordinate `x_resized`, input length `L_orig`, output length `L_resized`, and scale `s = L_resized / L_orig` or `1/scale` per schema interpretation, the public ONNX page gives: `align_corners: x_original = x_resized * (L_orig - 1) / (L_resized - 1)`; `asymmetric: x_original = x_resized / scale`; `half_pixel: x_original = (x_resized + 0.5) / scale - 0.5`; and the nearest default `round_prefer_floor`, which is “round half down.” citeturn49view1turn49view2turn49view3turn49view4

[DERIVED] For your use case, the dangerous combination is not floating drift in the abstract; it is a **one-index disagreement** caused by using the wrong `coordinate_transformation_mode` or a different half-tie rule in nearest sampling. That kind of mismatch is exactly the sort that survives into a single changed boolean cell after `output > 0.0`. citeturn49view1turn49view2

## Spec-vs-ORT deviation list

[PRIMARY] **Confirmed deviation: `Where` data-type support.** ONNX `Where` permits broad tensor types for `X/Y`; ORT CPU v1.24.4 visibly registers only a subset, and **does not visibly register `bool`**. The visible registrations are `uint8_t`, `int32_t`, `int64_t`, `float`, `double`, and `std::string` for opset 9–15, and a visible subset `uint8_t`, `int32_t`, `int64_t`, `float` for opset 16, with `MLFloat16` / `BFloat16` commented out in the shown code. For your exactness contract, this is not a numerical subtlety; it is a hard kernel-availability fault. citeturn50view0turn7view3

[DERIVED] **TopK `sorted=0` is under-specified in a way that matters.** The ORT CPU kernel explicitly orders ties by lower original index, but once `sorted=0` is chosen, ORT uses `std::nth_element` and does **not** do the final sort. So the “selected set” follows the comparator, but the order inside that set is not a portable semantic contract across STL implementations or backends. That is not a proven ORT-vs-ONNX violation; it is an implementation detail you should treat as unstable for exactness work. citeturn46view2turn50view2

[DERIVED] **Max/Min NaN behavior is a documentation hazard.** In the public ONNX operator pages I consulted, opset 12 and 13 are separate versions, but a NaN-rule paragraph was not surfaced; meanwhile ORT CPU visibly uses `Eigen::PropagateNaN` in the elementwise kernels I extracted, and I did not find a visible ORT CPU branch that changes NaN handling between opset 12 and 13. [DERIVED] **Pad negative-padding support looks broader in ORT than many users assume.** Because the common CPU path carries both `pads` and `slices` into `PadImpl(..., mode_, ...)`, crop-via-negative-pad is not confined to one special mode in the visible kernel path. The unresolved part is legacy-path proof for every opset/version combination, not the common path itself. citeturn50view1turn47view2turn47view3

[DERIVED] **Integer-domain “exact semantics” often come from host-language operators, not extra ORT guards.** `Div` uses native `/`; `Pow` uses `std::pow` and casts back; Add/Mul use native arithmetic operators. That makes negative integer division, signed overflow, and integer-cast edge cases especially dangerous when you want backend-portable bit-exactness. citeturn21view0turn21view1turn22view0

## Determinism and overall verdict

[DERIVED] For **single-threaded CPU inference** with optimizations disabled, I found **no evidence of intentional run-to-run nondeterminism** in the covered ORT CPU kernels. The biggest caveat is **semantic under-specification**, not randomness: `TopK(sorted=0)` is the clearest example because ORT intentionally skips the final sort after `nth_element`. On the same binary, same standard library, and same thread count, that often behaves reproducibly in practice; it is still not the kind of guarantee you should build an exactness contract on. citeturn46view2turn50view2

[DERIVED] Multi-threading is different. ORT CPU files in this area do use thread-pool parallel helpers in some kernels, and reduction code makes thread-pool-degree decisions in its fast paths; once you leave `intra_op_num_threads=1`, floating reduction order and chunking can become backend/build sensitive. Your stated configuration wisely avoids that class of nondeterminism. citeturn19view0turn44view2

[PRIMARY] **Overall verdict.** The top three silent breakage risks, ranked, are: **first, `Resize` coordinate/nearest mode mismatches**, because a one-index sample difference easily becomes a one-cell boolean difference after thresholding; **second, `TopK` and other tie-sensitive selection with under-specified ordering**, especially `sorted=0`; and **third, integer edge behavior in ORT’s native arithmetic paths**, especially `Pow` on integer tensors, negative integer `Div`, and any signed-overflow-adjacent computation. If I had to harden a model graph for bit-exactness against ORT CPU 1.24.4, I would eliminate `TopK(sorted=0)`, avoid integer-overflow-prone math, pin every `Resize` attribute explicitly, and never rely on `Where` with `bool` data tensors on CPU EP. citeturn49view1turn49view2turn46view2turn50view0turn21view0turn22view0
