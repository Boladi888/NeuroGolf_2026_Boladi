## Conv

[PRIMARY] Standard CPU `Conv` in `onnxruntime/core/providers/cpu/nn/conv.cc` is a float32 kernel. The source shown for the fast path prepares `MLAS_CONV_PARAMETERS`, allocates a working buffer as `sizeof(float) * WorkingBufferSize`, and calls `MlasConv` with `const float* Input`, `const float* Filter`, `const float* Bias`, and `float* Output`. The MLAS implementation entry point is likewise `MlasConv(const MLAS_CONV_PARAMETERS*, const float*, const float*, const float*, float*, float*, ...)`. That is a direct source-level confirmation that the standard CPU Conv compute path in this tag is float32, not MLFloat16. citeturn43view1turn43view4

[PRIMARY] Conversely, there is **no** `MLFloat16` registration in standard CPU `conv.cc`, and the CPU `nn/` directory does not show a separate standard fp16 Conv implementation file. [DERIVED] For the exact environment you gave—standard opsets 10–18 on CPU EP—that means there is **no source-backed native `Conv<float16>` kernel to trust**. The smallest “counterexample” is therefore structural rather than numeric: a minimal standard ONNX graph containing `Conv<float16>` on CPU EP does not have the standard CPU kernel registration this claim assumes. citeturn43view3turn32view0

[PRIMARY][DERIVED] On x86-64 specifically, the MLAS x86_64 tree lists float `SconvKernel*` and `SgemmKernel*` backends, but no fp16 Conv/HGemm family. Together with the ARM64-only `HGemmDispatch` assignment in `platform.cpp`, the source strongly indicates that the explicit fp16 MLAS matrix machinery is not an x86-64 standard-Conv CPU path. That makes the optimistic Conv claim unsafe twice over on your grader target: it is not only “not proven exact,” it is **not the registered standard CPU path at all**. citeturn28view0turn29view1

[DERIVED] For standard `Conv<float>` counting, the practical exactness rule is the ordinary float32 one: if every exact integer touched by the computation stays within the exact-integer `float32` range (`<= 16,777,216`), then integer counts remain representable. The smallest violating final integer is `16,777,217`, e.g. any scalar path that computes `16,777,216 + 1`. [PROMPT]

## Matrix products

[PRIMARY] CPU `MatMul` and CPU `Einsum` do **not** expose a standard `MLFloat16` path in the recovered v1.24.4 sources. In `matmul.cc`, the registered types shown are float/double/int32/int64 and the compute loop dispatches `math::MatMul<T>(...)`; `find` on that file returns no `MLFloat16` registration. In `einsum.cc`, the CPU dispatch branches shown are float, int32, double, and int64, and the device helpers it wires in for supported types are CPU `Transpose`, CPU `MatMul<T>`, CPU `ReduceSum<T>`, and CPU `DataCopy`. There is no CPU MLFloat16 branch there either. citeturn45view1turn45view3turn45view0turn45view4turn45view5

[PRIMARY] CPU `Gemm` is the important exception: `gemm.cc` does register `Gemm<MLFloat16>`. The recovered compute body has two paths: an fp16-acceleration branch guarded by `MlasFp16AccelerationSupported()` that calls `MlasHalfGemmBatch`, and a fallback branch that calls `math::Gemm<Eigen::half, CPUMathUtil>`. Separately, `MlasFp16AccelerationSupported()` returns true only when `MLAS_F16VEC_INTRINSICS_SUPPORTED` is compiled and runtime CPUID reports fp16 vector acceleration. citeturn11view0turn11view1turn11view2turn23view0turn23view1

[PRIMARY] The recovered MLAS half-GEMM **default dispatch** is not a hidden-fp32-accumulate kernel. Its scalar fallback loop initializes `float sum`, but then each multiply-add is explicitly passed through `MLAS_Float2Half(product + sum)` and converted back with `MLAS_Half2Float`, i.e. the running total is rounded to half **at every K-step**. The loop is left-to-right over `k`. `MlasHalfGemmGetDispatch()` returns the Neon dispatch only when both `MLAS_F16VEC_INTRINSICS_SUPPORTED` and `MLAS_TARGET_ARM64` are defined; otherwise it returns `MlasHalfGemmDispatchDefault`. citeturn25view0turn24view3turn31view0turn31view1

[PRIMARY][DERIVED] That gives a clean exactness rule for the recovered default MLAS half-GEMM path: **exact iff every partial sum is exactly representable in F16 under the source loop order, which is left-to-right in `k`**. The smallest violating example is a 1×2 dot product with exact products `2048` and `1`: for example `A = [2048, 1]`, `B = [1, 1]`, no bias. The exact result is `2049`; on the step-rounded half path, the first term is exact, and the first unavoidable rounding appears when the second add tries to leave the F16 exact-integer lattice at `2049`. citeturn25view0

[PRIMARY][DERIVED] x86-64 needs separate treatment. The x86_64 MLAS directory does not show fp16 HGemm kernels, while `platform.cpp` assigns `HGemmDispatch = &MlasHGemmDispatchNeon` under `MLAS_TARGET_ARM64`. That strongly points to the stock x86-64 CPU story being **the Eigen fallback**, not the ARM64 Neon HGemm path. I did **not** recover the exact Eigen half-matrix accumulation type from ORT source within this note, so I am **not** upgrading the x86 Eigen branch to either “final-output-only” or “partial-sum” with full confidence. The only safe builder rule I can defend from the recovered source is the conservative one: do **not** assume hidden extra precision for CPU `Gemm<MLFloat16>` on x86-64; at minimum the final stored result must itself be F16-representable, and if you need submission-grade guarantees, use `float32` or integer kernels instead. citeturn28view0turn29view1turn11view2

[DERIVED] For float32 matrix products, the x86_64 MLAS tree shows `SgemmKernelSse2`, `SgemmKernelAvx`, `SgemmKernelFma3`, and `SgemmKernelAvx512F`, so ORT’s optimized float matrix math on x86-64 is a SIMD/AVX/FMA-style float32 path, not an x87 extended-precision path. ## Quantized integer paths

[PRIMARY] `QLinearConv` is source-confirmed and is the strongest exact-count path I could verify at the operator-body level. The kernel registrations in `qlinearconv.cc` show `QLinearConv<uint8_t>` and `QLinearConv<int8_t>` with `T4 = int32_t` bias. In the non-symmetric path, the implementation comment explicitly says it uses an **intermediate `int32_t` buffer** “for the GEMM computation before requantizing to the output type,” allocates `sizeof(int32_t) * Y_offset`, calls `MlasGemm(...)` into that buffer, and then calls `MlasRequantizeOutput(...)`. In the symmetric path, it populates `MLAS_CONV_SYM_PARAMS` and calls `MlasConvSym` / `MlasConvSymDepthwise` with scale and output-zero-point information fused into the MLAS call. citeturn42view0turn42view1turn41view2turn42view2turn40view2turn40view5

[PRIMARY][DERIVED] For your stated exact-counter use case—`QLinearConv` with `scale = 1`, `zero_point = 0` and `uint8` output—the **raw accumulation** on the confirmed non-symmetric path is int32-exact, but the **stored output** is exact only while the post-requantization integer lies in the output tensor’s representable range. For `uint8`, that means **`0..255` exactly**; the smallest violating stored count is **`256`**. So your current informal rule *“exact ≤255 counter”* is the right practical bound for `uint8`-output `QLinearConv` with identity quantization. citeturn42view0turn41view2turn42view2

[DERIVED] If you need exact counts **above 255**, `QLinearConv<uint8>` is the wrong storage target even though the internal int32 accumulation can be exact before requantization. The right family to investigate next is `ConvInteger` / `MatMulInteger`, whose dedicated CPU files are present in the quantization directory. I did **not** recover their inner MLAS call sites within this note’s source budget, so I am not labeling their accumulator details as [PRIMARY] here. citeturn38view0

[DERIVED] The minimal exactness counterexamples for the quantized family are straightforward. For `QLinearConv<uint8>` with `scale=1`, `zero_point=0`, the first stored-output miss is any case whose true count is `256`. For an int32-output integer-conv or integer-matmul family, the first miss would be at int32 overflow rather than at 255, which is why those are the correct families for exact counts beyond 8-bit output range.

## Determinism and elementwise half semantics

[PRIMARY] CPU elementwise `Add`, `Sub`, and `Mul` **do** register `MLFloat16` kernels in `element_wise_ops.cc`, and the specialized compute bodies use Eigen half expressions directly. The recovered source shows `OutputEigen<Eigen::half>() = Input0 + Input1` for `Add<MLFloat16>`, analogous `Eigen::half` subtraction expressions for `Sub<MLFloat16>`, and `cwiseProduct` / scalar-product expressions for `Mul<MLFloat16>`. That is a direct source-level indication that these kernels are **not** wrapped in an ORT float32-upcast/float32-downcast helper; they execute as half-typed Eigen expressions and materialize a half output **per op**. citeturn47view5turn48view2turn48view1turn48view0

[PRIMARY][DERIVED] The exactness rule for F16 elementwise chains is therefore simple and strict: **every node in the chain must itself produce an exactly representable F16 integer result**. The smallest violating addition or subtraction is `2048 ± 1`, because `2049` is the first consecutive integer outside the exact F16 envelope. A smallest valid-integer multiply counterexample is `683 * 3 = 2049`: both inputs are exactly representable, but the exact product is not. citeturn48view0

[DERIVED] These elementwise kernels are also the easiest determinism case: they do not reduce across elements, so there is no summation-order reassociation issue. For fixed inputs, they are run-to-run deterministic. For the inspected Conv/GEMM/QLinearConv code, the source parallelizes over **disjoint output tiles or output tasks**: `MlasHalfGemmBatch` tiles M/N blocks, `MlasConv` segments output ranges, and `QLinearConv` parallelizes a fixed `task_count` over output chunks. With `intra_op_num_threads=1`, summation order is fixed by the single-thread kernel. With default threading, the inspected kernels still compute disjoint output regions rather than reducing one scalar from multiple threads, so run-to-run changes from thread interleaving are **not suggested by these source paths** for a fixed build and thread count. I did **not** recover an ORT CPU-wide document or issue guaranteeing more than that, so I would not claim a stronger universal guarantee than this source-local one. citeturn25view2turn43view4turn42view2turn48view0

## Design rules

[PRIMARY][REPLACED-BY] The design rule for standard CPU `Conv<float16>` in this environment is **not** “keep the result under 2048” and **not** “keep all partial sums under 2048.” It is: **do not use standard ONNX `Conv<float16>` on ORT 1.24.4 CPU EP x86-64 as a submission-grade exact counter, because the standard CPU kernel is not there.** Use `float32` Conv or an integer/quantized Conv family instead. citeturn43view3turn43view1turn28view0
